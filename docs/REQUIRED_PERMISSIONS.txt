================================================================================
AMAZON QUICK OBSERVABILITY PLATFORM
Required AWS IAM Permissions for Deployment on a New AWS Account
================================================================================

Audience: IT / Cloud administrators provisioning an IAM user or role for
whoever will deploy this repository (via deploy.py, scripts/setup_datacatalog.py,
scripts/create_topic.py, and cleanup.py).

This document lists the AWS permissions needed, grouped by what each
deployment step actually does. A ready-to-attach IAM policy document is in
iam-policy.yaml in this same folder. Read that file's header comments before
attaching it — it includes notes on scoping resources down after first
deployment.

Two access-control modes are supported for the data catalog step; pick ONE:
  A) IAM access control (recommended for most teams, simpler, no extra admin
     role needed)
  B) AWS Lake Formation (fine-grained column/table access control; requires
     the deploying identity to ALSO be a Lake Formation administrator, which
     is an account-wide privilege — see the note in Step 3 below)

--------------------------------------------------------------------------------
0. ONE-TIME ACCOUNT SETUP (usually done by an account admin, not the deployer)
--------------------------------------------------------------------------------

CDK Bootstrap (creates the CDKToolkit stack: a staging S3 bucket, an ECR
repository for container image assets, and a handful of IAM roles that CDK
itself uses to publish and deploy). Needed once per AWS account + region:

  - cloudformation:*                 (on stack/CDKToolkit/*)
  - s3:CreateBucket, PutBucketPolicy, PutBucketVersioning,
    PutEncryptionConfiguration, PutBucketPublicAccessBlock,
    PutLifecycleConfiguration                (on the bootstrap staging bucket)
  - ecr:CreateRepository, SetRepositoryPolicy, PutLifecyclePolicy
  - iam:CreateRole, PutRolePolicy, AttachRolePolicy, GetRole,
    CreatePolicy (on the small set of CDK bootstrap roles/policies)
  - ssm:PutParameter, GetParameter          (stores the bootstrap version)

If your organization already has CDK bootstrapped in the target account and
region for other projects, this step can be skipped entirely.

2. STEP 1 — CloudWatch Logs setup (deploy.py --logs)
--------------------------------------------------------------------------------

Creates: a customer-managed KMS key, 4 CloudWatch Log Groups, and the vended
logs delivery configuration that connects Amazon Quick to those log groups.

  - kms:CreateKey, DescribeKey, CreateAlias, DeleteAlias, EnableKeyRotation,
    GetKeyRotationStatus, PutKeyPolicy, GetKeyPolicy, ScheduleKeyDeletion,
    TagResource
  - logs:CreateLogGroup, DeleteLogGroup, DescribeLogGroups, TagResource,
    AssociateKmsKey, DisassociateKmsKey
  - logs:PutDeliverySource, GetDeliverySource, DeleteDeliverySource,
    PutDeliveryDestination, GetDeliveryDestination, DeleteDeliveryDestination,
    CreateDelivery, GetDelivery, DeleteDelivery, DescribeDeliveries,
    PutDeliveryDestinationPolicy, GetDeliveryDestinationPolicy
  - quicksight:AllowVendedLogDeliveryForResource   (REQUIRED — lets Amazon
    Quick send logs into your CloudWatch Log Groups)
  - quicksight:ListNamespaces, DescribeAccountSubscription, ListUsers
    (used to auto-detect the Amazon Quick subscription region and console
    users; read-only)

--------------------------------------------------------------------------------
3. STEP 2 — Data pipeline (deploy.py --pipeline)
--------------------------------------------------------------------------------

Creates: an S3 data lake bucket, 3 Lambda functions (2 Firehose transform
functions plus the scheduled Licensed_Users_Snapshot_Lambda), 5 Firehose
delivery streams, 2 EventBridge rules (the CloudTrail events rule and the
new daily Licensed Users Snapshot schedule that invokes
Licensed_Users_Snapshot_Lambda), IAM roles for
Lambda/Firehose/CloudWatch Logs/EventBridge, and CloudWatch Logs subscription
filters connecting Step 1's log groups to Firehose.

  - s3:CreateBucket, PutBucketPolicy, PutBucketVersioning, PutEncryption
    Configuration, PutBucketPublicAccessBlock, PutBucketOwnershipControls,
    GetBucketLocation, ListBucket, PutObject, GetObject,
    ListBucketMultipartUploads, ListMultipartUploadParts, AbortMultipartUpload
  - lambda:CreateFunction, UpdateFunctionCode, UpdateFunctionConfiguration,
    GetFunction, DeleteFunction, AddPermission, RemovePermission,
    TagResource, PublishVersion
  - firehose:CreateDeliveryStream, DescribeDeliveryStream,
    DeleteDeliveryStream, UpdateDestination, TagDeliveryStream
  - events:PutRule, DescribeRule, DeleteRule, PutTargets, RemoveTargets,
    TagResource
  - logs:PutSubscriptionFilter, DeleteSubscriptionFilter,
    DescribeSubscriptionFilters
  - iam:CreateRole, DeleteRole, GetRole, PutRolePolicy, DeleteRolePolicy,
    GetRolePolicy, AttachRolePolicy, DetachRolePolicy,
    ListAttachedRolePolicies, ListRolePolicies, TagRole,
    PassRole (needed so CloudFormation can assign these roles to Lambda,
    Firehose, and EventBridge)
  - kms:CreateGrant, RevokeGrant, ListGrants, Decrypt, Encrypt,
    GenerateDataKey, DescribeKey   (on the Step-1 KMS key — data lake and
    Firehose streams reuse it)

NOTE ON A KNOWN GAP FOUND DURING DEPLOYMENT:
The IAM role that CloudWatch Logs assumes to write into Firehose (created by
this stack) needs its own KMS Decrypt/Encrypt/GenerateDataKey grant on the
data lake key — not just the Firehose service role. If this permission is
missing, subscription filter creation fails with a KMS grant error even
though the KMS key and other IAM roles look correctly configured. This repo's
CDK code (cdk/pipeline_stack.py) already grants this; flagged here in case
your organization further restricts IAM policy content beyond what CDK
generates.

NOTE ON THE LICENSED USERS SNAPSHOT LAMBDA'S OWN PERMISSIONS — DEPLOY-TIME
vs. RUNTIME:
The list above is what the DEPLOYING identity needs to CREATE the pipeline
resources (the iam:CreateRole/PutRolePolicy/etc. actions already cover
creating a new IAM role and attaching a new policy, whatever its content).
It is a separate concern from what the Licensed_Users_Snapshot_Lambda's OWN
execution role is allowed to do once running. cdk/pipeline_stack.py already
creates a dedicated least-privilege role for this Lambda (separate from the
shared Firehose-transform Lambda role) granting only:
  - quicksight:ListUsers (Resource: "*" — QuickSight ListUsers has no
    resource-level ARN to scope to)
  - s3:PutObject scoped to
    arn:aws:s3:::<data-lake-bucket>/licensed-users-snapshot/*
  - kms:Encrypt, kms:GenerateDataKey on the Step-1 KMS key
No changes are needed in this document's Action lists for that role — it is
a RUNTIME grant defined inline in the CDK app, not something the deploying
identity's own IAM policy needs to enumerate.

4. STEP 3 — Data catalog (scripts/setup_datacatalog.py via deploy.py --datacatalog)
--------------------------------------------------------------------------------

Creates: a Glue database, 6 Athena tables, and 8 Athena views over the S3
data lake (including the licensed_users_snapshot table and the
licensed_users_activity / function_usage_distribution views added for the
Licensed Users pipeline and dashboard sheet).

  - glue:CreateDatabase, GetDatabase, DeleteDatabase, CreateTable, GetTable,
    GetTables, UpdateTable, DeleteTable, BatchCreatePartition
  - athena:StartQueryExecution, GetQueryExecution, GetQueryResults,
    StopQueryExecution, GetWorkGroup, ListWorkGroups
  - s3:GetBucketLocation, ListBucket, GetObject, PutObject
    (on the data lake bucket AND a separate bucket for Athena query results
    — create a dedicated query-results bucket if one doesn't already exist;
    it must be reachable/owned by the deploying account and region)

ACCESS CONTROL MODE — choose ONE:

  (A) IAM access control (--access-control iam): no further permissions
      needed beyond the above. Recommended unless column-level restrictions
      on sensitive chat content are required.

  (B) AWS Lake Formation (--access-control lakeformation): the deploying
      identity must ALSO be registered as a Lake Formation administrator
      (see: DataLakeAdmins in
      https://docs.aws.amazon.com/lake-formation/latest/dg/getting-started-setup.html#create-data-lake-admin ).
      This is an ACCOUNT-WIDE privilege affecting every Lake
      Formation-governed resource, not just this project — have your Lake
      Formation admin grant this deliberately, or use IAM mode instead if
      that's not something your organization wants to do casually.
      Additionally needs:
        - lakeformation:RegisterResource, DeregisterResource,
          DescribeResource, GrantPermissions, RevokePermissions,
          GetDataLakeSettings, PutDataLakeSettings
        - kms:PutKeyPolicy, GetKeyPolicy (to grant the Lake Formation
          service-linked role Decrypt/GenerateDataKey on the data lake key)
        - iam:GetRole (to verify the Lake Formation service-linked role
          exists before editing the KMS key policy)

    DescribeDataSourcePermissions, PassDataSource
  - quicksight:CreateDataSet, DescribeDataSet, UpdateDataSet, DeleteDataSet,

    dashboard owner's Quick Sight user ARN)

IMPORTANT — permissions that live OUTSIDE standard IAM and are easy to miss:

  1. The Quick Sight service role (aws-quicksight-service-role-v0, or
     aws-quicksight-s3-consumers-role-v0 if present) must be authorized, via
     Quick Sight's own "Manage Quick Sight -> Security & permissions ->
     AWS resources" setting, to access:
       - Athena (toggle on)
       - The specific S3 buckets used: the data lake bucket AND the Athena
         query-results bucket
     This is a separate customer-managed IAM policy
     (AWSQuickSightS3Policy) that Quick Sight's console UI maintains as an
     allow-list. New buckets are NOT added automatically — someone with
     Quick Sight admin rights must add them, either via that console screen
     or by editing the policy directly.

  2. Check for any existing Quick Sight IAM Policy Assignments in the
     account (quicksight:ListIAMPolicyAssignments /
     DescribeIAMPolicyAssignment) that apply to "all users" or "all groups".
     These act as SESSION POLICIES on top of the Quick Sight service role —
     they INTERSECT with (restrict, not add to) whatever the role's own IAM
     policies allow. A narrow pre-existing assignment (e.g. one scoped to
     only S3, set up for an unrelated purpose) will silently block Quick
     Sight's Athena access account-wide, even though standard IAM policy
     simulation reports the action as "allowed". If one exists, it needs to
     be broadened (not necessarily replaced) to include Athena/Glue access,
     or scoped to exclude the identity used for this deployment.

8. CLEANUP (cleanup.py)
--------------------------------------------------------------------------------

Needs delete/destroy permissions matching everything created above, plus:

  - quicksight:DeleteTopic
  - athena:StartQueryExecution (to run "DROP DATABASE ... CASCADE")
  - s3:DeleteObject, DeleteObjectVersion  (NOT bucket deletion — the data
    lake bucket and KMS key are retained by design; cleanup.py does not and
    should not delete them automatically)
  - lakeformation:DeregisterResource, RevokePermissions (only if Lake
    Formation mode was used)

--------------------------------------------------------------------------------
SUMMARY OF THINGS THAT ARE EASY TO OVERLOOK
--------------------------------------------------------------------------------

  1. quicksight:AllowVendedLogDeliveryForResource is a distinct, easily
     missed permission — without it, Step 1 fails silently on the vended
     logs delivery setup.
  2. Quick Sight's "AWS resources" S3 allow-list (see Step 4 note) is a
     separate authorization layer from IAM and is NOT covered by attaching
     an IAM policy alone — someone with Quick Sight admin rights must also
     enable Athena and add the S3 buckets through the Quick Sight console
     or by editing AWSQuickSightS3Policy directly.
  3. Pre-existing Quick Sight IAM Policy Assignments scoped to "all
     users"/"all groups" can silently block this deployment even with
     otherwise-correct IAM policies. Check for these BEFORE deploying Step 4
     if Athena connection tests fail with "not authorized" errors that
     don't match your attached IAM policies.
  4. If using Lake Formation access control, the deploying identity must be
     added as a Lake Formation administrator — an account-wide change,
     separate from any IAM policy — before Step 3 can succeed with that mode.
